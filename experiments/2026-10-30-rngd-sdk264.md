# RNGD resident cache migration to SDK 2026.4

Date: 2026-10-30. This migrates the custom `SwappableDecode` executable cache,
not Furiosa-LLM's FXB model loader. Onggi still supplies immutable checkpoint
diff ranges; the runtime owns native loading, row updates and rollback.

## Implementation and compatibility

The old loader imports `furiosa.native_torch.ir.Edf` and wraps `EdfModule`.
Those interfaces are absent from the inspected SDK 2026.4. Native
`furiosa.torch.ir.Runnable` exposes opaque serialize/deserialize methods.
The Python `CompileModule` wrapper additionally owns an output reconstructor.
Losing that metadata can change alias, passthrough or empty outputs after load.

New `.runnable` entries are single atomic archives containing version metadata,
native bytes and trusted Torch state. SDK/Torch versions are checked before
restoring payloads, and new caches use `CACHE/SDK/TORCH/KEY`. Old SDK 2026.2
entries retain the existing `CACHE/SDK/KEY.edf` and `.w` layout. Interrupted
publication leaves the prior entry intact. No vendor bytes are interpreted.

Export metadata contains FakeTensors that cannot be pickled. Only their shape,
stride and dtype are needed for reconstruction; plain meta tensors preserve
those descriptors without allocating data or mutating the live module. Default
`None` metadata and empty descriptor objects retain their different meanings.
The Python SDK wrapper has no public serializer, so the version adapter uses
its `_inner` field to reach the native serializer. This narrow boundary must be
revalidated on upgrades; uninspected SDK versions are not validated here.

Frozen initial code: `927c716fd295a42a13627302ebfef999f1a0deef`.
Reviewed metadata fix: `9c6e89293907beafff99d0951032156e667fe72a`.
Final cache writer: `0e6bb158a9ab3c40894df61e74fd0995d904a3d6`.
These fixes preserve optional output metadata and shared cache permissions;
graph definitions, serialized format and row-update code are unchanged.
New entries honor the builder's umask and atomic replacement preserves existing
permissions. The native RED was a 0600 entry under umask 022, which prevents
ordinary shared readers from opening a root-built cache. POSIX tests cover
027 -> 0640 creation and preservation of a private 0600 entry on replacement.

## Environment

furiosa-torch / furiosa-llm 2026.4.0, Torch 2.10.0+cpu, RNGD fusion 8/mesh 2.
An owned Kubernetes allocation provides one card; shared SDK, driver, original
provider and immutable checkpoint files remain unchanged. Loaded driver
srcversion matches the installed module built by the 2026.4 DKMS package for
the running kernel; the module exposes no version string, so this identity
check is recorded separately from installed package versions.

`verify_runnable_cache.py` compiles `z=x+y` returning `(z,z,x,x[:0])`, then a
separate process loads the cache with compilation explicitly forbidden. All
four outputs remain native tensors and equal independent CPU BF16 references.
The empty output is reconstructed and checked, not omitted from the comparison.

The source hashes and all four output hashes were independently checked.

An extra fresh-process probe returns `x[:,1:]` instead of `x`, covering a
nonzero passthrough offset and noncontiguous `[2,127]` view. Its compile/save
interval was 0.284673 s and fresh load 0.002237 s; all four outputs matched CPU
references on the device. Actual SDK default-`None` metadata also passed a

## Full-model protocol

Use Llama-3.1-8B-Instruct revision
`0e9e39f249a16976918f6564b8830bc894c89659`, B4/S256/**group2**, seed-0 eight-token
prompts and eight greedy tokens per stream. Compile new graphs in a fresh SDK
cache, then load fresh base/sparse-projection/sparse-LM references in separate
processes. Fixtures are the same immutable rows used in the
[2026.2 experiment](2026-10-23-rngd-row-update.md): down-projection rows `[0,64)`
and LM rows `[12041,12049)`. Hash the actual fixture files.

Each resident process performs `new → base → new → base`. Forbid graph
preparation after setup and verify shared/LM allocation and compiled-module
identity across updates. Synchronize native work and retain every timing sample,
including initial load and the first update. Native output hooks check devices;
inspect accepted logs for fallback/bridge/panic paths.

Then inject `KeyboardInterrupt` immediately after a real row copy. Require old
weights/token outputs to be restored, original allocations/modules retained,
the engine still usable after successful rollback, and stale KV rejected.
This validates asynchronous stream completion/rollback on 2026.4, separately
from CPU transaction tests.

## Compiler limits and full-model result

The original group8 bake exhausted a 64 GiB container. A separate owned
128 GiB allocation avoided OOM (observed peak 71,506,276,352 bytes), but the
native compiler rejected that graph with a `memory explosion` CompileError /
UnsupportedOpError. The configured unique-shape cap of 8 was accepted and is
not a memory limit. No speculative SDK compiler internals were changed.

The supported explicit group2 setting then baked successfully: decode
125.084 s / 760,632 bytes; LM head 29.920 s / 224,097 bytes. Source, artifact,
fixture and driver hashes are in [provenance](data/sdk264-resident-20261030/provenance.json).
The default constructor remains group8; use `group=2` and `Variant(4,256,2)`
for the configuration tested here. Other batch/context/group settings still
require their own compilation and validation.

Three separate fresh processes loaded base, sparse projection and sparse LM
checkpoints in 19.041, 19.467 and 19.797 seconds. All 96 generated tokens
also matched the earlier SDK 2026.2 reference files. This is an observed
cross-SDK token match for these inputs, not an accuracy evaluation.

Both resident cases passed four alternating updates, retaining device
allocations and compiled objects with no graph preparation. Projection row
updates uploaded 1,835,008 logical BF16 bytes; LM rows uploaded 65,536 bytes.
Both cases also restored base output after interruption following a real
native copy, retained allocations, and rejected stale KV.

[Every full-model run, token, timing sample and median](data/sdk264-resident-20261030/full-model.json)
includes the first update and every subsequent repeat. The final permission
fix is validated separately on the same baked graphs; the earlier results
remain recorded under their original source commit.

Final code repeated both cases: another eight updates / 256 generated tokens
matched fresh references, plus two interrupted-copy recoveries / 64 base
tokens. Across both code snapshots this is 16 updates / 512 update tokens
and four recoveries / 128 rollback tokens. Final runs also record native
`data_ptr()` values: every shared/LM pointer, Python tensor identity and
compiled-module identity stayed unchanged through updates and rollback.

Final-code medians include all four updates in each case:

| Changed rows | Logical upload | Application `delta_s` | Synchronized copy `copy_s` | Complete update | Through first token |
| --- | ---: | ---: | ---: | ---: | ---: |
| Projection, 64 rows | 1,835,008 B | 5.685 ms | 1.009 ms | 0.336 s | 0.501 s |
| LM, 8 rows | 65,536 B | 1.552 ms | 0.495 ms | 0.344 s | 0.504 s |

These describe the current path, without a same-SDK full-reload baseline.
The complete interval includes Onggi/checkpoint work outside `delta_s`.

Final tiny compile/save took 0.255224 s; fresh load with compilation forbidden
took 0.002197 s, with all four outputs matching. The actual POSIX permission
probe passed 027 -> 0640 and preserved 0600 on replacement; a new default-022
archive was also readable by the ordinary non-root host user.

Initial full-model loading is separate from resident replacement. These runs
prove the smaller update works on SDK 2026.4; they do not establish a cold-load
speedup or a performance improvement over SDK 2026.2. SDK, Torch and grouping
changed together. Complete update includes live Onggi comparison, planning and
checkpoint handling; `delta_s` includes staging/validation/rollback preparation
as well as synchronized native copy. Neither it nor logical payload bytes is
a PCIe/DMA-only measurement.

## Review and CPU validation

Seven cache regressions failed on the old implementation, then passed after
the port. An independent whole-branch reviewer found one Important default
metadata case; the new regression reproduced the failure and passed after the
`None` guard. Final writer CPU suite on Windows: 304 passed, 8 skipped,
4 subtests passed (two new POSIX permission checks are skipped there).
[Frozen final-code Linux CI](https://github.com/ai-computing/rngd-pd/actions/runs/40981727987)
passed 308 tests, skipped 2 and passed 4 subtests before the permission tests.
[Final writer Linux CI](https://github.com/ai-computing/rngd-pd/actions/runs/40985385628)
passed 310 tests, skipped 2 and passed 4 subtests, including both POSIX checks.
Native SDK 2026.2 execution
was not repeated in this allocation because its old venv is not mounted; the
legacy implementation remains covered by the cache round-trip regression and
the prior hardware validation scope.

## Ownership and cleanup

The initial OOM allocation and replacement allocation were never concurrent.
After capture, the owned Pod and namespace were deleted with UID preconditions.
Independent API checks confirm namespace absent, owned Pods absent and zero
owned RNGD resource requests. All experiment processes ended; source worktrees
were clean. The obsolete source uploader was stopped and its owned terminal
closed. The original provider and its checkout were untouched.
